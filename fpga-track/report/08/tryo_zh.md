# Tryo 硬件加速架构与部署方案说明

## 1. 系统设计目标

Tryo 是面向 AMD KV260 边缘 FPGA 平台构建的视觉-语言模型推理加速系统。系统目标是在资源受限、功耗受限的板端环境中，完成紧凑型 VLM 的端到端推理部署，并尽可能提高文本解码阶段的吞吐、能效和运行稳定性。

视觉-语言模型的推理过程通常包含两个性质不同的阶段：图像侧特征提取和语言侧自回归解码。图像编码器在一次请求中通常只运行一次，计算图相对复杂，软件生态依赖较多；语言解码器则在每个生成 token 时反复执行，具有高度重复的层级结构和稳定的数据访问模式。Tryo 因此采用 PS-PL 协同架构：Host/PS 侧负责灵活的请求准备和服务管理，PL 侧负责高频、规则、可流式化的解码计算。

该设计没有把 FPGA 仅作为一个孤立矩阵乘法加速器使用，而是将其组织成面向 Transformer 解码器的板端计算引擎。PL 端持续维护解码所需状态，Host 侧只负责准备输入、发起调用和接收输出，从而减少逐层软件调度开销，并提高整个推理路径的可重复性和可部署性。

## 2. 整体硬件加速架构

Tryo 的系统由 Host 运行时、板端权重与缓存组织、PL 解码器加速逻辑三部分组成。

Host 侧完成图像输入、视觉 token 生成、文本 prompt 组织、tokenizer 处理、OpenAI 兼容服务封装以及评测脚本调度。视觉编码器和 prompt 处理保留在 Host 侧，可以降低 PL 资源压力，并允许系统在不重新综合硬件的情况下调整输入格式、服务接口和测试脚本。

PL 侧实现文本解码器的主要计算路径。对于 SmolVLM2 类模型，文本解码器包含多层 Transformer block，每层由归一化、Q/K/V 投影、RoPE、attention score、softmax、value 聚合、输出投影、前馈网络和残差更新构成。这些算子具有稳定的数据依赖关系，适合在 FPGA 上实现为静态控制的数据流结构。

在 PL 内部，Tryo 将解码器划分为四个主要功能单元：

- **存储管理单元 MMU**：负责输入 hidden state、打包权重、KV cache、logits 输出和中间缓冲区的地址组织与数据搬运。
- **数据流控制单元 DCU**：负责不同计算阶段之间的数据路由、投影结果分发、注意力路径与前馈路径切换，以及流式执行顺序维护。
- **向量处理单元 VPU**：负责 Q/K/V projection、attention score、value mixing、FFN projection 等向量密集计算。
- **标量处理单元 SPU**：负责 RMSNorm、RoPE、softmax 相关处理、激活函数、量化/反量化辅助逻辑和残差更新。

这种模块划分体现了模型结构和硬件结构之间的对应关系：MMU 管理数据位置，DCU 管理数据走向，VPU 处理大规模线性计算，SPU 处理逐元素与标量变换。各模块并不是松散拼接的算子集合，而是围绕完整解码器执行顺序组织的协同流水。

## 3. PL 端算子选型与映射

Tryo 的 PL 端算子选择遵循两个原则。第一，优先硬件化重复执行频率高、数据流稳定、对吞吐和时延影响大的算子。第二，避免将软件控制复杂、请求相关性强、变化频繁的部分固化到 PL 中。

### 3.1 Attention 路径映射

Attention 是解码器中最关键的计算路径之一。Tryo 将 Q/K/V projection、RoPE、attention score 计算、softmax 处理和 value 聚合映射到 PL 端执行。其中，projection 和 score/value 计算由 VPU 承担，RoPE 和 softmax 相关逐元素操作由 SPU 承担，KV cache 的读写由 MMU 统一管理。

这种映射方式能够避免 Host 在每层 attention 内部参与细粒度调度。对 Host 而言，PL 端表现为一个可调用的解码器执行单元；对硬件而言，attention 内部则按照固定顺序进行流式推进。

### 3.2 Feed-Forward 路径映射

FFN 部分包含 gate、up、down 等线性投影，以及激活和逐元素组合操作。Tryo 将线性投影映射到 VPU，将激活、门控和残差相关操作映射到 SPU。由于 FFN 在每层中都固定出现，且权重访问和输入输出形状稳定，因此适合采用离线权重打包和板端顺序读取的方式实现。

### 3.3 归一化、RoPE 与残差更新

RMSNorm、RoPE 和残差更新虽然单个操作的算术密度不如矩阵乘法高，但它们位于关键路径上。如果这些操作频繁回退到 Host，会破坏解码器流水并增加数据往返。因此 Tryo 将其保留在 PL 端，通过 SPU 与 VPU 协同执行，减少中间状态搬运。

### 3.4 KV Cache 管理

KV cache 是自回归解码中的核心状态。Tryo 在 PL 侧维护和访问 KV cache，Host 不参与每一步 cache 更新。这样可以降低 Host-PL 往返控制开销，也避免在 decode 阶段频繁搬运历史 token 状态。

## 4. GQA 结构的硬件映射

模型采用 grouped-query attention。该结构中 query heads 数量多于 key/value heads，多个 query heads 共享同一组 K/V。直接将 K/V 扩展到与 Q 相同数量会增加权重读取、缓存容量和计算开销，不符合边缘 FPGA 的资源约束。

Tryo 在硬件映射中保留 GQA 的共享 K/V 语义。以 15 个 query heads 和 5 个 K/V heads 为例，每 3 个 query heads 共享一个 K/V head。权重打包和硬件调度均按照这一分组关系组织，使共享 K/V 在片上保持一致的生命周期。

对于每个 GQA 分组，Tryo 在离线打包阶段安排 Q、共享 K、共享 V 的读取顺序，使其与 PL 端数据流消费顺序一致。这样可以减少额外暂存，避免把共享 K/V 复制成多个物理副本，也让 DCU 在分发投影流时能够按照确定规则路由。

这一点是系统的一个重要设计亮点：GQA 不只是模型层面的结构压缩，而是被进一步落实到权重布局、缓存组织和硬件调度顺序中。也就是说，模型结构、离线转换脚本和 PL 控制逻辑共享同一套数据组织规则。

## 5. Host-PL 协同方案

Tryo 的 Host-PL 协同分为请求准备、硬件执行和结果返回三个阶段。

在请求准备阶段，Host 读取输入图像，调用视觉 token 生成工具得到图像表示；随后根据用户文本构造 prompt，并通过 tokenizer 和 embedding 相关逻辑形成解码器输入。该阶段保留在软件侧，便于适配不同输入、评测任务和服务接口。

在硬件执行阶段，Host 将输入状态、权重路径、缓存地址和控制参数准备好，然后调用 PL 解码器执行。PL 端按固定层级顺序执行 Transformer block。执行过程中，KV cache、hidden state 和 logits 缓冲均由板端运行时和 PL 逻辑协同维护。Host 不需要在每层内部反复下发细粒度命令。

在结果返回阶段，PL 输出 logits 或解码所需中间结果，Host 完成 token 选择、文本拼接和服务响应。对于评测任务，Host 还负责记录吞吐、TTFT 和功耗采样结果。

这种协同方式具有三个优点：

1. **降低调度开销**：Host 不参与每层内部算子调度，减少 decode 阶段控制往返。
2. **保持软件灵活性**：输入格式、服务接口和评测脚本仍然可以在 Host 侧快速调整。
3. **增强部署稳定性**：PL 端执行顺序固定，权重布局固定，运行时行为更容易复现。

## 6. 量化与权重组织

为了适配 KV260 的片上资源和外部存储带宽限制，Tryo 使用低比特权重表示和离线打包策略。权重转换过程不仅改变数值精度，也改变张量在硬件中的读取顺序。

权重文件在部署前被转换为硬件友好的连续流格式。Q/K/V、输出投影和 FFN 权重按照 PL 消费顺序重排，并与 GQA 分组关系保持一致。这样做可以减少运行时索引计算，并降低硬件数据路由复杂度。

量化方案采用 W5A8 作为工程折中。相比更高精度表示，W5A8 能显著降低权重存储和搬运压力；相比更激进的 W4A8，它在输出分布保真度和 top-k 结果稳定性上更可靠。因此，该量化选择不是单纯追求低比特，而是在资源、带宽和推理质量之间取得平衡。

## 7. 部署流程

Tryo 的板端部署由镜像环境、overlay 文件、运行时目录和评测脚本共同组成。

首先，板端系统需要具备 PYNQ/XRT 运行环境，并能够通过 bitstream 配置 PL。部署目录中包含对应的 `.bit`、`.bit.bin` 和 `.hwh` 文件，用于加载硬件设计并提供寄存器和接口描述。

其次，运行时目录包含 PL 所需的权重文件、tokenizer 文件、视觉 token 工具、Python 驱动脚本和服务脚本。启动服务前，脚本会设置必要的环境变量，包括 bitstream 路径、权重目录、tokenizer 路径、AXI 基地址和服务最大生成 token 数。

最后，通过板端脚本完成评测。典型流程是：

1. 加载 bitstream。
2. 设置 PL 时钟到目标频率。
3. 启动 OpenAI 兼容本地服务。
4. 运行 throughput、energy 和 TTFT 测试脚本。
5. 保存评测结果 JSON。

在最终测试中，系统工作在 300 MHz PL 时钟下，完成了吞吐、功耗和 TTFT 三类板端评测。

## 8. 方案亮点

Tryo 的主要亮点可以概括为以下几点。

第一，系统采用清晰的 PS-PL 协同边界。Host 处理灵活输入与服务逻辑，PL 处理重复且规则的解码计算，从而避免把不适合硬件固化的部分强行放入 FPGA。

第二，PL 端不是单一 GEMM 加速器，而是围绕完整 Transformer 解码器构建的专用数据流架构。MMU、DCU、VPU 和 SPU 分别承担存储、路由、向量计算和标量处理职责，使解码路径能够持续推进。

第三，GQA 的共享 K/V 结构被完整保留并映射到硬件数据流中。权重打包、KV cache 组织和 PL 调度顺序保持一致，减少了重复缓存和不必要的数据搬运。

第四，量化和权重布局与硬件执行顺序协同设计。W5A8 权重表示降低了存储和带宽压力，离线打包则降低了板端运行时的索引和调度复杂度。

第五，系统具备完整的板端部署与评测闭环。通过 bitstream、运行时脚本、权重文件和评测程序，可以在 KV260 上完成端到端推理、吞吐测试、能耗测试和 TTFT 测试。

## 9. 总结

Tryo 面向边缘 FPGA 上的视觉-语言模型推理需求，构建了一套软硬件协同的加速方案。系统没有将所有模块简单硬件化，而是根据计算规律和部署需求进行任务划分：Host 侧保留输入处理和服务灵活性，PL 侧承担高频解码计算和状态维护。

在 PL 端，Tryo 将 Transformer 解码器拆分为存储管理、数据流控制、向量处理和标量处理四类功能单元，并通过离线权重打包、GQA 感知映射和低比特量化使模型结构与硬件数据流保持一致。该方案兼顾了资源约束、运行稳定性和端到端可部署性，体现了面向实际 FPGA 板端推理系统的工程化设计思路。
